# QA skills: `qa-docs` and `qa`

Agent-driven acceptance QA of a web app in a real browser: `qa-docs` writes and maintains what to check, `qa` checks
it — clicking through scenarios, with screenshots judged by a separate agent — and `deliver` closes a run with it.

**Status:** implemented · **Proposed:** 2026-10-29, commit `3d04cb8` · **Modules:** qa-docs (new), qa (new), [deliver](../../../../skills/deliver/SKILL.md), [finish](../../../../skills/finish/SKILL.md), [feature](../../../../skills/feature/SKILL.md), [help](../../../../skills/help/SKILL.md)

## Why

The flow has features, spec scenarios, contract tests and reviews, but nothing confirms that the assembled
application works for a user: that the screens render, the layout holds, and the flows across features succeed. E2E
tests cover what someone scripted; nobody looks at the app. An agent with a browser can — if it knows what to check
and someone other than the clicking agent judges the result.

## Scope

- **In:** web apps only; `qa-docs` (create and maintain `docs/qa/`), `qa` (scripted run of feature acceptance criteria
  and journeys, exploratory run), browser tool mapping per host, Playwright in the recommended plugins, a QA stage in
  `deliver`, pointers from `finish`, `feature` and `help`. One release, 1.10.0, after all three milestones.
- **Out:** mobile and desktop drivers (the driver table gets a row when needed), QA in `docs-check` and `health`,
  scripts (`qa_status.py`, a `docs/qa` lint) — see the decision, generated per-AC check files, visual regression
  against baseline images.

## Decision

| Option | Summary | Effort | Main risk |
|--------|---------|--------|-----------|
| One `qa` skill with modes | Authoring and running in one `SKILL.md` | M | A long procedure with four modes; authoring would need the browser setup it does not use |
| **A — `qa-docs` + `qa`, Markdown only** | Pair like `spec-docs` + `spec-tests`; format in `qa-docs/references/qa-format.md`, briefs in `qa/references/briefs.md`; the agent reads coverage from run reports | M | Journey IDs and links may drift without a lint |
| B — A plus scripts | `spec_lint.py --qa` (anchors `J<n>`, AC links) and `qa_status.py` (last result per ID) | L | Freezes the format in code before it is proven on real projects |

**Chosen: A.** The skill-authoring guideline makes a mode that changes the procedure a separate skill; authoring is
cheap and runs after every feature, a browser run is expensive and needs a running app. Shortcut: no scripts until
the format has held for a few runs — then add B's lint and status script.

Decisions taken with the user (2026-10-29):

- **Name** `qa` (not `qa-agent`, not `manual-qa-lead`): every skill is run by an agent; "manual" misleads.
- **Host-agnostic boundary, web-only driver.** Scenario format, judge and report do not depend on the tool; only the
  executor does. `qa` holds one driver table with one row (web → browser tool from the host mapping). A non-web app
  → "no driver", stop. No untested instructions for other platforms.
- **What to check = feature AC + journeys + app-wide rules.** Acceptance criteria stay on the feature pages and are
  executed from there (with the scenarios in `**Realised by:**` for detail) — no copies. `docs/qa/journeys.md` holds
  cross-feature paths `J<n>` written as intent ("add a product to the cart"), not selectors. `docs/qa/index.md` holds
  what neither has: environments and how to start the app, test accounts and data, roles, app-wide UI rules
  (viewports, empty / error / loading states, i18n), and links to the feature catalogue and journeys. No screen map:
  it would go stale; exploration finds screens.
- **Feature AC win.** An app that disagrees with an AC is a FAIL. A journey that disagrees with an intended change is
  `OUTDATED`, fixed by `qa-docs`; when unsure, ask (in `deliver`: save a `p2` issue).
- **Separate judge.** The executor collects evidence; a subagent with fresh context gets only the expectations, the
  app-wide rules and the screenshots — never the executor's narrative. Console errors and 4xx/5xx responses are
  collected as cheaper, deterministic evidence next to the images.
- **Sequential.** One browser session is shared state: one executor subagent per scenario, one after another.
- **Screenshots:** reports in `docs/qa/runs/` are committed; screenshots of FAIL and `OUTDATED` checkpoints are
  committed next to the report as evidence for issues; the rest go to a gitignored working directory.
- **Safety:** only localhost or an environment listed in `docs/qa/index.md`; any other URL → ask; never production.
- **Nested subagents:** a `deliver` stage runs as a subagent, which cannot start subagents — so the loop runs the QA
  stage itself in the main thread, following `qa/SKILL.md`.
- **`finish` only points to `qa`**, no new step or gate: a browser run is expensive and needs a running app.

## Scenarios

**Module:** qa-docs

### <a id="QAD-R1"></a>QAD-R1 — Maintain what QA checks

**Change:** 🆕 added

> `qa-docs` **SHALL** create and keep `docs/qa/index.md` and `docs/qa/journeys.md` in line with the code and the
> feature pages, writing only after the user approves.

#### <a id="QAD-001"></a>QAD-001 — First run creates docs/qa

**Kind:** ✅ happy · **Change:** 🆕 added

- **Given** a web app without `docs/qa/`
- **When** the user runs `qa-docs`
- **Then** it drafts `index.md` and `journeys.md` from the routes, roles and UI conventions in the code, the feature
  pages and `AGENTS.md`, asks only what the code cannot tell (accounts, test data, critical paths), and writes after approval

#### <a id="QAD-002"></a>QAD-002 — Drift on an existing docs/qa

**Kind:** ✅ happy · **Change:** 🆕 added

- **Given** an existing `docs/qa/`
- **When** the user runs `qa-docs`
- **Then** it lists drift — routes and AC no journey or feature covers, journeys naming removed screens or roles —
  as suggestions, and writes the accepted ones

#### <a id="QAD-003"></a>QAD-003 — Coverage from runs

**Kind:** ✅ happy · **Change:** 🆕 added

- **Given** run reports in `docs/qa/runs/`
- **When** the user runs `qa-docs`
- **Then** it shows the last result per AC and journey: PASS, FAIL, OUTDATED or never run

#### <a id="QAD-004"></a>QAD-004 — Outdated journey

**Kind:** ⚠️ edge · **Change:** 🆕 added

- **Given** a run marked a journey step `OUTDATED`
- **When** `qa-docs` runs
- **Then** it proposes the journey fix, unless the fix contradicts a feature AC — then it offers a `bug` issue instead

#### <a id="QAD-005"></a>QAD-005 — AC too vague to run

**Kind:** ⚠️ edge · **Change:** 🆕 added

- **Given** an acceptance criterion that names no observable outcome
- **When** `qa-docs` runs
- **Then** it suggests a journey for it (or sharpening the AC with `as:feature`), and never edits the feature page

#### <a id="QAD-006"></a>QAD-006 — Stable journey IDs

**Kind:** ⚠️ edge · **Change:** 🆕 added

- **Given** journeys `J1…Jn`
- **When** a journey is removed or added
- **Then** IDs are never renumbered or reused; a removed journey keeps its text with the removed status

#### <a id="QAD-007"></a>QAD-007 — Not a web app

**Kind:** ❌ error · **Change:** 🆕 added

- **Given** a project with no web front end
- **When** the user runs `qa-docs` or `qa`
- **Then** it says no driver supports the app and stops

**Module:** qa

### <a id="QA-R1"></a>QA-R1 — Verify the app in a browser

**Change:** 🆕 added

> `qa` **SHALL** execute acceptance criteria and journeys in a browser, judge the evidence independently, and report
> each result with proof.

#### <a id="QA-001"></a>QA-001 — Targets

**Kind:** ✅ happy · **Change:** 🆕 added

- **Given** `docs/qa/index.md`
- **When** the user runs `qa docs/features/<slug>`, `qa journeys`, `qa J<n>`, `qa branch` or `qa explore <area>`
- **Then** it runs that feature's AC, all journeys, one journey, the AC and journeys touched by the branch's
  changes, or an exploratory session of the area

#### <a id="QA-002"></a>QA-002 — No docs/qa

**Kind:** ❌ error · **Change:** 🆕 added

- **Given** no `docs/qa/index.md`
- **When** the user runs `qa`
- **Then** it stops and suggests `qa-docs`

#### <a id="QA-003"></a>QA-003 — No browser tool

**Kind:** ❌ error · **Change:** 🆕 added

- **Given** the host has no browser tool
- **When** `qa` starts
- **Then** it stops with the install step from the host mapping

#### <a id="QA-004"></a>QA-004 — App not running

**Kind:** ❌ error · **Change:** 🆕 added

- **Given** the app does not answer at the configured URL
- **When** `qa` starts
- **Then** it stops with the start command from `docs/qa/index.md`

#### <a id="QA-005"></a>QA-005 — Unsafe URL

**Kind:** ❌ error · **Change:** 🆕 added

- **Given** a URL that is not localhost and not an environment listed in `docs/qa/index.md`
- **When** `qa` starts
- **Then** it asks before opening it, and refuses one marked production

#### <a id="QA-006"></a>QA-006 — Executor per scenario

**Kind:** ✅ happy · **Change:** 🆕 added

- **Given** a scripted run with several scenarios
- **When** they execute
- **Then** each runs in its own executor subagent, one after another, recording at every checkpoint a screenshot,
  console errors and failed network responses

#### <a id="QA-007"></a>QA-007 — Independent judge

**Kind:** ✅ happy · **Change:** 🆕 added

- **Given** an executed scenario
- **When** it is judged
- **Then** a subagent with fresh context gets only the expected outcomes, the app-wide UI rules and the evidence, and
  returns PASS, FAIL or OUTDATED per checkpoint with a reason

#### <a id="QA-008"></a>QA-008 — Report and evidence

**Kind:** ✅ happy · **Change:** 🆕 added

- **Given** a finished run
- **When** it is reported
- **Then** `docs/qa/runs/<date>-<target>.md` lists every scenario with its result; FAIL and OUTDATED screenshots are
  saved next to it, the rest in a gitignored working directory

#### <a id="QA-009"></a>QA-009 — FAIL becomes an issue

**Kind:** ✅ happy · **Change:** 🆕 added

- **Given** a FAIL
- **When** the run ends
- **Then** it offers a `bug` issue with the steps, the expected and actual outcome and the screenshot, prioritised by
  the issue rubric, `**Source:**` `as:qa`

#### <a id="QA-010"></a>QA-010 — App disagrees with a scenario

**Kind:** ⚠️ edge · **Change:** 🆕 added

- **Given** the app behaves differently from a scenario
- **When** it is judged
- **Then** a mismatch with a feature AC is a FAIL; a journey step that no longer matches an intended change is
  OUTDATED and goes to `qa-docs`

#### <a id="QA-011"></a>QA-011 — Exploratory run

**Kind:** ⚠️ edge · **Change:** 🆕 added

- **Given** `qa explore <area>`
- **When** it runs
- **Then** the executor tries to break the area (empty and invalid input, double submit, back and refresh mid-flow,
  narrow viewport, long text) and reports findings only, each with reproduction steps and evidence

#### <a id="QA-012"></a>QA-012 — Host without subagents

**Kind:** ⚠️ edge · **Change:** 🆕 added

- **Given** a host without subagents
- **When** `qa` runs
- **Then** scenarios run in the main thread and judging is a separate pass after all of them, on the evidence only;
  the report says the judgement was not independent

**Module:** [deliver](../../../../skills/deliver/SKILL.md)

### <a id="DLV-R1"></a>DLV-R1 — QA closes a run

**Change:** 🆕 added

> `deliver` **SHALL** verify the delivered work with `qa` when the project has `docs/qa/index.md`.

#### <a id="DLV-001"></a>DLV-001 — QA stage

**Kind:** ✅ happy · **Change:** 🆕 added

- **Given** `docs/qa/index.md` and a clean final review
- **When** the loop picks the next stage
- **Then** it runs a QA stage in the main thread — `qa docs/features/<slug>` for a feature run, `qa branch` for an
  issues run

#### <a id="DLV-002"></a>DLV-002 — QA failures are fixed in the run

**Kind:** ✅ happy · **Change:** 🆕 added

- **Given** a QA stage with FAIL results
- **When** it ends
- **Then** each FAIL is saved as a `p2` or `p3` issue, becomes a run issue, is fixed by the loop and QA runs again; a
  FAIL that comes back after its fix stops the run as no progress

#### <a id="DLV-003"></a>DLV-003 — QA cannot run

**Kind:** ⚠️ edge · **Change:** 🆕 added

- **Given** no browser tool, or an app that cannot be started from `docs/qa/index.md`
- **When** start-up checks the host
- **Then** it says QA will be skipped, and the report marks the QA criterion as skipped, not failed

#### <a id="DLV-004"></a>DLV-004 — Done needs a clean QA run

**Kind:** ✅ happy · **Change:** 🆕 added

- **Given** QA ran in this run
- **When** the done criteria are checked
- **Then** the last QA run has no FAIL; OUTDATED results are listed in the report for `qa-docs`

#### <a id="DLV-005"></a>DLV-005 — Unsafe URL is human-only

**Kind:** ❌ error · **Change:** 🆕 added

- **Given** a QA target URL that is not localhost and not a listed environment
- **When** the QA stage starts
- **Then** the stage is blocked with the question; QA is not run against it
