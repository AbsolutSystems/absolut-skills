# Page format

Explain pages carry content only. Styling lives in `docs/explain/explain.css`; diagrams are Mermaid, rendered in the
browser. Use only the elements and classes listed here.

## Rules

- HTML5, UTF-8, `<html lang="en|pl">` matching the page language. Title: `<kind>: <subject>`.
- Exactly one stylesheet, `<link rel="stylesheet" href="explain.css">`, and exactly one script, the last line before
  `</body>`, copied as is:

  ```html
  <script type="module">import mermaid from "https://cdn.jsdelivr.net/npm/mermaid@11/dist/mermaid.esm.min.mjs"; mermaid.initialize({ startOnLoad: true, theme: matchMedia("(prefers-color-scheme: dark)").matches ? "dark" : "neutral" });</script>
  ```

  Shortcut: Mermaid loads from a CDN, so diagrams render only online (offline the diagram source stays readable);
  upgrade to SVG rendered at write time if pages must work offline.
- Forbidden: `<style>`, `style="…"`, other `<script>`, `<svg>`, `<img>` with data URIs, presentational attributes,
  classes not listed below.
- Indent with 2 spaces; one block element per line; no comments except the marker
  `<!-- as:explain kind=<kind> for=<audience> -->` as the first line of `<head>`.
- Escape `<`, `>`, `&` in text and in diagram source — the browser parses tags inside `<pre>` before Mermaid reads
  it. In a `flowchart`, every node and edge label in double quotes (`a["Reserves the pool"]`,
  `-->|"what flows"|`), a line break as `&lt;br/&gt;`; unquoted parentheses or brackets in a label break the diagram.
  In a `sequenceDiagram`, messages and `participant … as …` names stay unquoted (quotes would show) and avoid `;` and `#`. Code references as `<code>path:symbol</code>` — never line
  numbers, they move. Links are relative (spec pages: `../spec/<…>.md`, features: `../features/<slug>/index.md`).

## Vocabulary

| Element / class | Use |
|-----------------|-----|
| `<header>` + `<h1>` + `<p class="lead">` | Title and the answer in 1–3 sentences |
| `<dl class="meta">` | Kind, audience, date, base and head or commit, sources, link to the PR, feature or spec page |
| `<section id="…">` + `<h2>` | Sections below, with these `id`s; headings in the page language |
| `<figure class="diagram">` + `<pre class="mermaid">` + `<figcaption>` | One diagram; the caption says what to look at |
| `<table>` with `<thead>`; `class="num"` on numeric cells | Before/after, matrix, code map |
| `<article class="example" id="E1" data-kind="happy\|change\|edge" data-status="matches\|differs\|to-confirm">` | One worked example (card below) |
| `<dl class="gwt">` | Fields of a card: input, rule, calculation, result, source |
| `<pre class="formula"><code>` | A formula written as a spreadsheet cell |
| `<span class="badge">` | Short label: scenario ID, criterion `AC<n>`, status |
| `<aside class="note">` | Caveat: not checked, assumption, offline diagrams |
| `<details>` + `<summary>` | On `business` pages: developer detail (code references, names) folded away |
| `<footer>` | Generated by `as:explain`, date, how to regenerate |

## Example card

```html
<article class="example" id="E2" data-kind="change" data-status="to-confirm">
  <h3>Rate changes in the middle of the quarter</h3>
  <dl class="gwt">
    <dt>Input</dt>
    <dd>120 kg in January at 0.40 per kg, 80 kg in March at 0.45 per kg</dd>
    <dt>Rule</dt>
    <dd>Each month is charged at the rate valid in that month, rounded once at the end</dd>
    <dt>Calculation</dt>
    <dd><pre class="formula"><code>=ROUND(120*0.40 + 80*0.45; 2)</code></pre></dd>
    <dt>Result</dt>
    <dd>84.00</dd>
    <dt>Source</dt>
    <dd>Calculation from <code>sources/rates.xlsx</code>, sheet Q1, B4:C5; no test yet</dd>
  </dl>
</article>
```

Status: `matches` — the code (a test) gives the same as the source or criterion; `differs` — it does not (say both
numbers); `to-confirm` — a hand calculation or a rule the business has to confirm.

## Sections

Required unless marked "if". An empty required section says why in one line ("No migrations in this change").

**Change** (`change-…`) — for a reviewer or a stakeholder; explains, never judges (findings belong to `as:review`):

| `id` | Content |
|------|---------|
| `tldr` | What changed and why in 5–8 sentences; what the user sees differently |
| `scope` | Base ← head, commits, files grouped by module, and what the change does **not** cover |
| `before-after` | Table: behaviour or structure before and after |
| `architecture` | if the structure changes (below): one delta diagram of the components before and after |
| `how` | The mechanism: who calls whom, where the decision is; one diagram |
| `examples` | if it calculates, converts or decides by thresholds: example cards for the changed rule |
| `data` | if migrations, schema or stored data change: what, reversible or not, steps after deploy |
| `tests` | What covers the change (test names, scenario IDs), CI status; explain runs nothing |
| `risks` | Deliberate shortcuts, deferred parts, rollout and `**Verify:**` items of the proposal |
| `questions` | if any: what the reader should ask the author |

**Module** (`module-…`) — for a newcomer:

| `id` | Content |
|------|---------|
| `tldr` | What the module or behaviour does, for whom, in 3–5 sentences |
| `context` | Where it sits: callers, dependencies, data it owns; one diagram |
| `flow` | The main flow step by step; one diagram |
| `rules` | The business rules, each with its spec scenario ID when one exists |
| `examples` | if it calculates, converts or decides by thresholds: example cards |
| `errors` | Edge cases and error paths: what the user sees |
| `code-map` | Table: concept → `path:symbol`; on `business` pages inside `<details>` |
| `questions` | if any: behaviour the spec does not define or the code leaves unclear |

**Feature** (`feature-…`) — for the business, on worked examples:

| `id` | Content |
|------|---------|
| `scope` | What is verified and what not, the sources used, the acceptance criteria covered |
| `happy` | Cards for the basic cases: data complete, everything as expected |
| `changes` | if data can change after it is entered (rate, quantity, period, cancellation): cards for what happens then |
| `edge` | Cards for zeros, limits, missing data, period boundaries, thresholds — each with a result |
| `matrix` | Table of all cards: ID, case, input in short, result, status; numbers equal to the cards |
| `validation` | if the feature rejects or warns: rules and the exact messages the user sees |
| `diagram` | The path of a number from input to result, or the decision flow; one diagram |
| `questions` | Open questions with the options and what each implies; do not answer them |

## Content rules

The measurable checks (sections, numbers, markup) pass on their own; whether a person understands the page does not.
The default mistake is copying the code's vocabulary right after reading it.

| Field | Carries | Check |
|-------|---------|-------|
| node label, card title | **what happens**, a verb phrase in the language of the problem | reads like a sentence, not an identifier |
| sublabel (second line of a node) | **why it matters**, or what it works on | does not paraphrase its own label |
| edge label | **what flows** (data, a decision), not the target's name | does not repeat a node label |
| code name | only in `<code>path:symbol</code>` in prose or the code map | never on a diagram of a `business` page |

```text
Wrong:  "lockApplicable" / "pool taken before contract"     Right: "Reserves the contract's pool" / "so nobody else takes it"
Wrong:  "remaining()" / "counts rest for 409"               Right: "Counts what is left in the pool" / "only for the error message"
```

Do not shorten by cutting words until a label fits; rewrite it at a higher level. Diagrams:

- one idea per diagram, at most about 15 nodes; collapse steps the reader does not need into one group node and say
  in the caption what it contains;
- `flowchart` for decisions and data paths, `sequenceDiagram` for calls between parts;
- a before/after pair only when the **order** of steps is the point (a step that undoes an earlier one, a read
  between writes of one transaction, a lock released too early); otherwise the `before-after` table is enough.

### Architecture delta

Draw it when the change's diff adds or deletes files outside tests, moves a function or class between files or
modules (a rule changes owner), touches two or more modules, or removes a public function, class or endpoint. Skip it
for a change in one file, tests only, a rename or reformat, or under ~50 lines in one module — and say so in one line
in `before-after`.

One `flowchart` holds the union of both states: components (modules, services, stores, external systems) as nodes,
dependencies as edges. A component that exists in both states keeps **one node ID**, so it reads as unchanged rather
than removed plus added. Mark the difference with these classes, defined in the diagram source and listed in the
caption as the legend:

```text
classDef added stroke:#2e7d4f,stroke-width:3px
classDef removed stroke:#b3261e,stroke-width:2px,stroke-dasharray:6 4,color:#b3261e
classDef moved stroke:#1f4b99,stroke-width:3px
classDef changed stroke:#a15c00,stroke-width:3px
```

- `added`, `removed` — the component appears or disappears; a removed edge is drawn `-.->` with its label
  ending "(removed)".
- `moved` — a responsibility changes owner: the node where it lands, with the sublabel naming where it came from.
- `changed` — same responsibility, different contract or behaviour; say what in the sublabel.
- Unchanged components stay plain and only as many as the reader needs to place the change.

Under the diagram, a table: component, change (added / removed / moved / changed), what it means for the reader.
Above about 15 nodes, draw two diagrams, before and after, with the same node IDs and order instead of one delta.

Before the page is done, read the diagram labels alone, in order: someone who does not know this code should read
them as a description of the flow.
